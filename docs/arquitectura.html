§ 1

Principio y alcance

Vista 360° es una capa propia sobre el ecosistema existente. No reemplaza sistemas: lee los datos de los sistemas fuente y añade la información y la funcionalidad de acompañamiento, que hoy no existe en ningún lado.

La vista se compone en el backend, no en el frontend. Un Backend for Frontend (BFF) orquesta y agrega la información; el frontend nunca habla directamente con el ERP ni con el LMS. Eso concentra en un solo lugar la composición, la resiliencia y la autorización, y deja al cliente sin conocimiento del ecosistema.

§ 3

Para cada dato: de dónde sale y por qué

Regla general: cada dato se toma de su fuente de verdad. Lo que cambia es cómo se trae —en vivo, con cache, o como proyección alimentada por eventos— según su volatilidad y su sensibilidad.

DatoFuente de verdadCómo lo obtiene Vista 360°Por qué así
Identidad / login Plataforma de Identidad OIDC (Authorization Code + PKCE) Es la fuente y usa estándares abiertos; no se replican credenciales.
Datos personales ERP API mediada, on-demand + cache corta Fuente de verdad; cambian poco; toleran cache.
Datos académicos
(matrícula, notas, condición)		 ERP API on-demand + proyección local por eventos/CDC Lectura frecuente; la proyección desacopla y habilita analítica y el servicio de la Parte 2.
Estado financiero ERP API síncrona on-demand, sin persistir Dato volátil y sensible; el usuario necesita el valor exacto «ahora» (Escenario 3.2.A).
Actividad en el campus virtual LMS · cloud API del LMS mediada; cache con TTL medio Sistema externo; tolera algo de latencia de frescura.
Reportes, alertas y solicitudes de acompañamiento Vista 360° — propio Base de datos propia No existen hoy en ningún sistema; son nuevos.
Asignación asesor ↔ estudiante Vista 360° — propio Base de datos propia (semilla desde RRHH/ERP) Es la base de la autorización del equipo de acompañamiento.
Alimentación del Data Warehouse Todos los sistemas Eventos + CDC → tópicos → sink (ELT) El DWH no consulta las bases transaccionales ni al revés.
§ 4

Cómo se comunican los componentes

Dos estilos, cada uno donde corresponde: síncrono para «leer ahora», asíncrono para «propagar un cambio». Ni todo REST ni todo eventos.

EnlaceEstiloMecanismo y seguridad
Frontend → BFFSíncronoREST/HTTPS + JWT de OIDC (token de usuario).
BFF → servicios de dominioSíncronoREST interno (o gRPC), mTLS + token de servicio (client credentials), red privada.
Vista 360° → ERP / LMSSíncronoAPI mediada por la Plataforma de Integración. Timeout + circuit breaker + degradación parcial.
ERP → Vista 360°AsíncronoEvento publicado en el broker; Vista 360° se suscribe.
Vista 360° → otros procesos / DWHAsíncronoTransactional Outbox → broker → consumidores + sink. Entrega at-least-once, idempotencia por eventId, partición por studentId.

§ 5

Decisiones más importantes

DecisiónFundamento
BFF que agrega en el backendUna sola llamada del frontend; composición, resiliencia y autorización en un lugar; el cliente no conoce el ecosistema.
Acompañamiento como fuente de verdad de lo nuevo, con BD propia (PostgreSQL)Es la única información que Vista 360° posee; el resto lo lee de los sistemas fuente.
Proyección académica local por eventos/CDCDesacopla a Vista 360° de la disponibilidad del ERP para lecturas frecuentes y habilita el DWH. El servicio de la Parte 2 se construye sobre ella.
Estado financiero siempre en vivo desde el ERP, sin persistirDato volátil y sensible; la exactitud manda.
Síncrono para «leer ahora», asíncrono para «propagar cambios»Cada estilo donde corresponde.
Transactional Outbox para publicar eventosPublicación confiable sin dual write entre la BD y el broker.
DWH alimentado por eventos/CDC, no por consultasEl almacén analítico no se acopla a las bases transaccionales.
Identidad delegada a la plataforma OIDCEstándar abierto; Vista 360° es resource server, no IdP.
Autorización a nivel de recurso, evaluada en el backend con el tokenEl frontend no es de fiar; la relación asesor ↔ estudiante se verifica contra datos propios.
§ 6

Supuestos declarados

El caso es abierto a propósito. Ante lo que no está definido, se asume lo razonable y se declara:

#Supuesto
S1La Plataforma de Integración expone las APIs mediadas del ERP y del LMS y ofrece un broker de eventos/mensajería.
S2El ERP puede emitir eventos o se le puede aplicar CDC; si no, hay fallback de polling/batch.
S3La Plataforma de Identidad soporta OIDC (Auth Code + PKCE) para usuarios y client credentials para servicios.
S4Vista 360° es solo lectura sobre ERP y LMS; solo es fuente de verdad de la información de acompañamiento.
S5La asignación asesor ↔ estudiante nace en RRHH/ERP y se sincroniza; mientras tanto se administra en Vista 360°.
S6Para la Parte 2, el servicio usa su propia BD con datos de ejemplo, que representa la proyección alimentada del ERP.
S7Volúmenes moderados (decenas de miles de estudiantes) → PostgreSQL es suficiente.
S8El frontend es una SPA web (posible app móvil a futuro).
S9Los datos académicos y financieros oficiales se leen del ERP; Vista 360° no los recalcula.
